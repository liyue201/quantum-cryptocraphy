# 哈希签名：只用哈希的防弹衣

前一篇我们看到：签名的安全如果建立在"离散对数/大数分解难"上，就会被 Shor 一把掰断。那有没有一种签名，**根本不依赖这些数学难题**，只用哈希哈希——而哈希恰恰是量子只能平方根加速、无法反向扭转的？答案是 **哈希签名（Hash-Based Signatures, HBS）**。这一章我们亲手搭一个最朴素的版本：**Lamport 一次性签名**，然后讲清楚它如何扩展成能多次签名的 SPHINCS+（NIST 已标准的后量子签名之一）。

> 核心思想一句话：**先把"要签的内容"哈希成一个位串，然后用"每比特都对应一把秘密钥匙"的方式来回答 '是 0 还是 1'。** 哈希的单向性保证：敌人就算拿到签名，也看不到那些没有被用到的秘密，所以无法伪造。

## Lamport：一次性签名的最短版

假设消息被哈希成 8 位（`01001101`）。Lamport 的做法：

1. **密钥生成**：为**每一位**都造两个随机秘密（一个代表"这一位是 0"，一个代表"这一位是 1"）。8 位 → 造 16 个秘密。
2. **公开公钥**：把这 16 个秘密各自哈希，得到 16 个哈希值作为公钥。
3. **签名**：看消息每一位是 0 还是 1，**只在对应那把秘密**上签名（公开出来）。
4. **验证**：把收到的秘密哈希一下，和公钥对应位是否对得上。

> 为什么安全？验证者只看得到"被用到的那些秘密的哈希"。而哈希是**单向**的：看到哈希，推不出秘密。敌人若想伪造，必须拿出"没有被用到的那一比特的秘密"——但他只见过哈希，算不出来。所以他签不出你能验证通过的内容。

## 为什么只能签一次

因为签名会**泄露**秘密：消息每一位都是确定答案，签名后就相当于公开了这 8 位中"被选中的那一半"秘密。如果再用同一把钥匙签**另一条**消息，两条消息不同比特的组合，就可能让你把另一条消息也"拼"出来 → 可伪造。所以这类签名是**一次性**的（One-Time Signature，OTS）。

> 这就带来现实难题：真实世界的账户要签很多笔。怎么办？—— SPHINCS+ 的"多层哈希树"就是为此而来。

## 从一次性到 SPHINCS+：一棵"签名工厂"的树

- 用一根根哈希树，把上千个"一次性密钥对"组织起来，根节点认作公钥。
- 每次签名用树里一个**新的 OTS 密钥对**，并用一棵轻量哈希树（WOTS+ 签名 + 认证路径）证明"我是根的孩子"。
- 一次性密钥用完即弃，**每个密钥只签一次** → 无数笔交易，安全性却不受"多次使用"拖累。

> 打开右侧代码：我们用 Python **完整实现一个精简版 Lamport 一次性签名**（用字节哈希做消息，按若干比特签名、验证），并现场演示三件事：正常签名能验证通过、**篡改消息立刻验证失败**、以及用**同一把钥匙签第二条不同消息时会被判定为可疑/泄露**（这正是为什么必须一次性使用）。看完你就懂 SPHINCS+ 为什么非搞哈希树不可。

## 为什么不干脆全员都用哈希签名

哈希签名很硬核，但有两个"死穴"：
- **公钥/签名体积非常大**（SPHINCS+ 签名可达几 KB），比 ECDSA 的几十字节胖几十倍，交易成本高、区块膨胀。
- **有状态性**：有些 HBS 需要维护"已用到哪个密钥"的状态，跨设备管理麻烦（无状态版本缓解了此问题，但实现复杂）。

所以现实里哈希签名常用于**固件签名、代码签名、短期密钥**等场景；网络通信的常态加密/密钥交换，更多交给下一章的**格密码**（LWE/Kyber/Dilithium），它们体积小、无状态，成为主流方向。

```
Lamport 一次性签名
  私钥 = 每比特两把随机秘密
  公钥 = 每把秘密的哈希      ← 只存哈希
  签名 = 每比特拿出被选中的那把秘密
  验证 = 哈希签名对公钥各比特   ← 单向性保安全
→ 缺点：只能签一次 → SPHINCS+ 用哈希树叠成千上万次
```

## 边界提示

本章实现的是教学版 Lamport（比特数少、示意），真实 WOTS+/SPHINCS+ 在比特粒度、哈希函数选择、状态管理上有大量工程细节。你只要抓住主线：**哈希签名把安全支点从"可被 Shor 破解的数学难题"换成"唯有单项哈希"，量子对它只能平方根加速、无法角度破解**——这就是「只用哈希做防弹衣」的全部秘密。
